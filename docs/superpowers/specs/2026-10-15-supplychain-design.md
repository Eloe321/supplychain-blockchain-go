# Go supply chain blockchain design

Approved scope: a learning and capstone project implementing a custom proof of work blockchain in Go, with libp2p networking, batch provenance and custody, CLI and HTTP API. The user approved the design and authorized specification, planning, and subagent implementation on 15 October 2026.

## Scope and choices

Build the ledger and consensus rules ourselves. Use libp2p for authenticated encrypted transport, peer discovery and GossipSub; use bbolt for transactional local storage. Raw TCP would require recreating connectivity and transport protections. A permissioned framework would obscure the custom blockchain mechanics central to this project.

The application tracks whole batches through supplier, manufacturer, carrier, distributor and retailer organizations. Auditors can inspect the ledger. It records claims about custody; it cannot verify physical goods. Manufacturing transformations, quantity splitting or merging, payments, smart contract languages, dynamic actor enrollment, and a browser UI are outside this first version. Quantity and unit remain fixed after creation.

## Packages and contracts

The module is `supplychain`. Public packages are `ledger` (pure consensus and supply chain rules), `chain` (persistent block graph, canonical state and mempool), `node` (libp2p networking and mining), and `api` (local HTTP interface). `cmd/supplychain` supplies the executable. Tests use real signatures, storage and local libp2p hosts.

### Ledger

`Config` contains `ChainID string`, `Difficulty uint8`, and `Participants []Participant`. Each participant has `ID`, `Name`, `Role`, and `PublicKey` strings; IDs are the hex SHA256 digest of the decoded Ed25519 public key. Participant roles are `supplier`, `manufacturer`, `carrier`, `distributor`, `retailer`, and `auditor`. Config validation rejects duplicate identities, invalid keys and roles, empty chain IDs, and difficulty outside 1 through 24. A normalized sorted participant list defines the configuration hash and deterministic genesis block. Tests use difficulty 4; the demo defaults to 12. Difficulty is fixed by genesis, never chosen by an incoming block.

`Event` is a fixed-field struct with `Version int`, `ChainID`, `Kind`, `BatchID`, `Actor`, `Recipient`, `Name`, `Unit`, `Location`, `Status`, `DocumentHash`, `PreviousEvent` strings; `Quantity int64`, `Sequence uint64`, `Timestamp int64`, `ID`, and `Signature` strings. JSON uses explicit snake_case field names without omitempty. Signing uses an explicit fixed-field payload omitting ID and signature, with a version and chain domain; the SHA256 payload digest is the ID and Ed25519 signs that payload. No maps or floating point values enter consensus encoding. Hex values are canonical lowercase. Signature validation resolves the actor key from the genesis participant registry.

Event kinds are `create`, `checkpoint`, `offer`, `accept`, and `cancel`. Create requires supplier or manufacturer, positive quantity, nonempty name and unit, sequence 1 and no predecessor. A new batch belongs to its creator. Checkpoint updates location, status and optional document digest and requires current ownership. Offer names an enrolled nonauditor recipient other than the owner and records a pending transfer. Accept must be signed by that pending recipient and changes ownership. Cancel must be signed by the owner. While a transfer is pending only accept or cancel is allowed. Every update references the last event ID and increments the batch sequence by exactly one; unused action fields must be empty to avoid ambiguous signed intent. An actor cannot forge recipient acceptance or transfer another organization's batch. `State` is a map from batch ID to `Batch`, containing immutable creation fields, owner, pending recipient, latest location/status, sequence and last event ID. Apply functions mutate only after full validation succeeds.

Event strings and payloads are bounded: batch ID 128 bytes, actor IDs and predecessor hashes 64 hex characters, name 128 bytes, unit 32 bytes, location 256 bytes, status 64 bytes, document digest empty or 64 hex characters. Timestamp is positive; consensus does not rely on wall-clock time for event ordering. A full event is at most 16 KiB.

`Block` contains version, chain ID, height, previous hash, timestamp, fixed difficulty, nonce, Merkle root, ordered events and hash. An explicit header encoding commits to every header field and the Merkle root. Merkle hashing domain-separates leaves and internal nodes and duplicates an odd last node at every level. Genesis is an unmined deterministic anchor: fixed timestamp, nonce zero, no events, and previous hash equal to the normalized configuration hash. Its identity must be identical across nodes and must match the locally derived genesis exactly; only blocks at height one and above require proof of work. Incoming blocks must match the stored hash, proof target, expected difficulty, parent and height, nondecreasing timestamps, Merkle root, and all sequential event transitions. Equal block timestamps are valid: height and parent links determine order. This permits extension even after a valid block uses the maximum int64 timestamp, preventing a finite timestamp range from making the chain terminal. Mining callers use the greater of the current time and the parent timestamp without incrementing the parent timestamp. Blocks are limited to 256 events and 1 MiB. Empty mined blocks are allowed so the demo can show confirmations and fork resolution. Mining accepts context cancellation.

### Chain

One bbolt database per node stores config, all validated blocks including side branches, and the canonical tip. The chain exposes copied immutable values and protects shared state with a mutex. Each validated block retains an independently derived immutable state snapshot from its own parent. Candidate validation uses that parent snapshot, never unrelated canonical custody state. Startup replays and verifies the complete stored graph to reconstruct these snapshots. This makes branch validation and switching simple for a small capstone dataset, at the cost of retaining a batch map per block; large deployments would need state pruning or checkpoints.

Select greatest verified cumulative work. Fixed per-network difficulty means height is equivalent to cumulative work; an explicit work calculation documents this rule. Equal work selects the lexicographically smaller tip hash. On a winning branch change, atomically persist the block and tip, select its independently validated state snapshot, remove confirmed mempool events, and revalidate pending events plus detached events. Invalid or conflicted detached events are dropped. The database remains unchanged on a failed validation or write. Startup validates stored config and blocks and derives canonical state rather than trusting disk state blindly.

The mempool is bounded to 4096 events. It rejects confirmed duplicates, duplicate IDs, invalid signatures and transitions. Pending events are validated sequentially against canonical state plus accepted pending events; conflicts against the same prior batch version are rejected. Revalidation uses deterministic dependency-aware passes. Queries include tip, height, work, batches, batch trace, pending IDs, confirmation counts and canonical blocks. Local mining uses a snapshot and then revalidates the result under the chain lock, retaining a valid side branch if the tip changed meanwhile.

### P2P node

Every node can dial, accept, validate and relay; mining is optional. A persistent libp2p key identifies the host separately from organization event signing keys. TCP with Noise and stream multiplexing is sufficient; disable unused transports where it simplifies resource use. Chain-scoped protocol IDs and topics isolate networks. A handshake checks protocol version, configuration/genesis hash and chain ID before sync. Ledger validation remains authoritative even when transport is authenticated.

Support multiple bootstrap multiaddresses, a persisted peer cache, bounded peer exchange, retry with bounded exponential backoff, optional mDNS for LAN, and application-scoped Kademlia discovery for WAN. Discovery is opt-in where appropriate for reproducible local tests. Bootstrap peers introduce nodes and do not decide ledger validity. GossipSub uses distinct transaction and block announcement topics with content ID deduplication, bounded validators and queues. Validate events before accepting/relaying them; only verified blocks become canonical. Announcements trigger request/response retrieval where needed; missed gossip is repaired by periodic synchronization.

A bounded sync stream exchanges status, block locators, and batches of up to 32 blocks. Find a common ancestor, fetch parent-first, validate locally and retry another connected peer after timeout. Do not trust advertised height, work or state. Unknown-parent announcements trigger sync, rather than unbounded orphan storage. Late joining and restarted nodes catch up automatically. Synchronization handles competing branches and uses chain fork choice after validation. Mempool anti-entropy exchanges bounded pending inventories so startup and reconnection recover unconfirmed work.

Resource limits include 1 MiB blocks, at most 2 MiB wire frames, 16 KiB events, 64 peer addresses per exchange, bounded peer cache, at most 64 connections, per-peer request throttling, read/write deadlines, bounded concurrent sync requests and bounded gossip queues. Reject oversized frames before allocation. Decode strict JSON request structs and return errors for malformed or unsupported requests. Context cancellation closes goroutines and network resources. Avoid holding chain locks during network operations or proof of work.

For WAN deployments configure public announced addresses or explicit reachable relay candidates, Circuit Relay v2 and optional hole punching. A bounded relay mode must be available. NAT/firewall traversal cannot be guaranteed; describe exactly which local integration cases ran and provide instructions for a separate multi-host WAN check.

### Interfaces and demo

CLI commands generate actor keys, initialize shared genesis configuration, run a node, inspect status/peers, create signed events, submit them to an HTTP endpoint, mine, and query batches/traces. CLI keys are stored with mode 0600 and never sent to nodes through the API. The HTTP API accepts signed events only and binds to loopback by default; explicitly exposing it requires deliberate configuration. Administrative mining is local demo functionality. API handlers have timeouts, body bounds, strict decoding, JSON errors, and explicit status codes. Invalid requests must not panic or silently mine bad events.

Deliver a deterministic reproducible demo that generates disposable keys and shared config, starts at least three independent processes with separate databases, creates and transfers a batch, checks matching tips and histories, and shuts down only processes it started. Include Makefile targets for build, test, race, vet, and demo. Document HTTP routes, CLI examples, module boundaries, consensus, tutorial mapping, deployment/NAT configuration and limitations. Include Docker packaging or equivalent multi-host instructions if useful, without claiming WAN verification from a localhost test.

## Verification and acceptance

1. Pure ledger tests reject altered signatures and fields, unauthorized and stale custody changes, duplicate batches, invalid Merkle roots and proof of work. Recipient acceptance and cancellation work with actor permissions enforced.
2. Storage tests prove restart persistence, config mismatch rejection, atomic failed updates, sibling branches, longer-chain and deterministic equal-work selection, state rollback and mempool conflict handling.
3. Local real-host network tests cover transaction and block propagation across multiple hops, late joining, missing-block catch-up, continued operation after bootstrap loss, same-height competing forks and partition/reconnect convergence with conflicting custody events.
4. Protocol tests reject wrong chain/genesis and incompatible parameters; malformed, oversized, duplicate and stalled traffic does not crash or hang the node.
5. CLI/API smoke tests exercise actual signed batch creation and two-party transfer. The executable multi-process demo completes without shared databases or a central validation service.
6. Final checks run `go test ./...`, `go test -race ./...`, `go vet ./...`, a clean build and the demo. Report any unverified WAN condition explicitly.
